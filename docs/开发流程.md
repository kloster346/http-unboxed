# 开发流程规范（http-unboxed）

本仓库采用「main + dev」双层分支模型（Git Flow 简化版）。请你务必遵守本规范。

## 分支角色

| 分支 | 角色 | 是否直接开发 | Pages 是否更新 |
|------|------|-------------|---------------|
| `main` | **稳定/交付基线**（默认分支） | ❌ 否，只接受 PR 合并 | ✅ 是（push 后自动部署） |
| `dev`  | **日常开发中心** | ✅ 是，所有改动在此 | ❌ 否（PM 看不到） |

> 因为 GitHub Pages 只部署 `main`，所以在 `dev` 上的开发**不会影响线上正式版**，只有合并进 `main` 才更新给用户。

## 日常开发（每天的习惯动作）

```bash
git checkout dev          # 切到开发分支
git pull origin dev       # 先同步最新，避免冲突

# ...改代码...

git add <文件>             # 或 git add .
git commit -m "说明你的改动"
git push origin dev       # 推到远端 dev
```

## 发布 / 合并进 main（攒够一版时）

```bash
# 1. 确认 dev 已推好、测试通过

# 2. 创建 PR：dev -> main（用 gh 一键）
gh pr create --base main --head dev --title "版本/功能说明" --body "改动内容"

# 3. 在 GitHub 上查看 diff、确认无误

# 4. 合并 PR（merge）→ 自动 push 到 main → Pages 自动重新部署
```

合并后，PM 打开 https://kloster346.github.io/http-unboxed/ 即可看到最新版。

## 重要约定（禁止事项）

- ❌ **永远不要**在 `main` 上直接提交/推送。
- ❌ 不要绕过 PR 直接 `git push` 到 `main`。
- ✅ 每个功能或问题，做成一个独立的 PR，便于回看和审查。
- ✅ 提交信息写清楚做了什么（如 `feat: 增加xx`、`fix: 修复xx`）。
